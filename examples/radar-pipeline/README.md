# radar-pipeline

End-to-end FMCW radar signal-processing pipeline: a UDP front-end streams chirp
IQ into Tomii, which runs range/Doppler FFTs, CA-CFAR detection, and clustering,
then verifies detections against the scene ground truth and reports frame
latency/jitter. The DSP kernels live behind a C ABI (`kernels/radar.h`) with two
interchangeable implementations — **FFTW on the CPU** and **cuFFT on the GPU** —
so the same graph and verifier run on either by swapping the kernel `.so`.

## Graph topology

```
$network ─► range_fft   (factor=n_chirps, 1 packet = 1 chirp)
            │              window + range FFT, corner-turned into the rd buffer
            ├─► doppler_fft (factor=n_tiles, $barrier on all range_fft)
            │              per-tile chirp-axis FFT + power map
            ├─► cfar        (factor=n_tiles, $barrier on all doppler_fft)
            │              2D CA-CFAR over the tile's range rows
            └─► cluster     (factor=1,       $barrier on all cfar)
                           strongest-cell-per-cluster detection list
```

One UDP packet carries one chirp (a 64-byte header + `n_samples` interleaved
i16 I/Q). The receiver assigns packets to a frame slot by `frame_id` and to a
chirp index by `chirp_id`; a frame is complete once all `n_chirps` packets
arrive. `slots` frames are processed concurrently (the rd/power/detection
buffers are sized `frame_wnd = slots` and indexed `frame_id % frame_wnd`).

## Requirements

- Rust toolchain, Python 3.10+
- **CPU kernel:** FFTW single-precision (`libfftw3f-dev`, for `pkg-config fftw3f`).
  If FFTW's dev files aren't system-installed (no `fftw3.h` / `fftw3f.pc`) but
  live in a conda env, point the build at them, e.g.:
  ```bash
  export PKG_CONFIG_PATH=$HOME/miniconda3/envs/radar/lib/pkgconfig
  export LD_LIBRARY_PATH=$HOME/miniconda3/envs/radar/lib   # so the .so resolves at runtime
  ```
- **GPU kernel (`--gpu`):** NVIDIA GPU + CUDA 12 with cuFFT (`nvcc`); the
  `kernels/Makefile` defaults to `CUDA_ARCH=sm_89` — override for other GPUs,
  e.g. `make -C kernels gpu CUDA_ARCH=sm_80`.

## Build and run

`run_bench.py` builds everything (kernels via Make, the plugin + `tomii-core`
via Cargo), generates the graph from the scene, starts the receiver, then the
sender, verifies, and prints latency percentiles. The scene is auto-generated on
first run if missing.

```bash
# From repo root — CPU pipeline (FFTW):
python examples/radar-pipeline/run_bench.py --frames 400

# GPU pipeline (cuFFT) — identical graph and verifier, kernel .so swap:
python examples/radar-pipeline/run_bench.py --gpu --frames 2000 --frame-period 0.005 --warmup 50

# Sweep concurrency (each cell is verifier-gated):
python examples/radar-pipeline/run_bench.py --sweep-workers 2 4 8 --sweep-slots 1 2 4
```

Pick a GPU with `CUDA_VISIBLE_DEVICES=<id>` for the `--gpu` runs.

## Scenes

Scenes are synthetic and reproducible; the binary IQ (`data/out*/`) is
git-ignored and regenerated by the script.

```bash
# Default scene (1024 samples x 128 chirps):
python examples/radar-pipeline/data/make_scene.py

# Large-CPI scene (4096 x 512, 16x compute) used for the CPU-vs-GPU crossover.
# Custom targets keep velocities inside the (larger CPI) unambiguous range:
python examples/radar-pipeline/data/make_scene.py \
    --n-samples 4096 --n-chirps 512 --n-frames 150 --frame-interval 0.010 \
    --target 30,2.0,20 --target 75,-3.0,25 --target 120,1.0,30 \
    --out-dir examples/radar-pipeline/data/out_big

# Point a run at a specific scene:
python examples/radar-pipeline/run_bench.py --gpu \
    --scene examples/radar-pipeline/data/out_big/scene.json
```

The sender (`sender.py`) paces chirps at the scene's physical `chirp_interval_s`
so packets stream across the CPI like a real front-end. This matters:
back-to-back bursting a whole frame can overrun the receiver's UDP socket buffer
(kernel-capped at `net.core.rmem_max`), dropping chirps. Pass `--chirp-gap-us 0`
to force a single burst per frame. For very high packet rates, raise the cap
(`sudo sysctl -w net.core.rmem_max=67108864`).

## Verify

The benchmark is **verifier-gated**: a latency number is reported only when
every ground-truth target is detected in every processed frame *and* the frame
count matches (coverage). `verify.py` parses the detection dump and checks it
against the scene:

```bash
python examples/radar-pipeline/verify.py \
    --scene examples/radar-pipeline/data/out/scene.json \
    --detections examples/radar-pipeline/results/detections_s2_w8.txt \
    --expect-frames 400
```

`TOMII_VERIFY_PATH` tells the `cluster` node where to dump per-frame detections
(set automatically by `run_bench.py`). Setting `TOMII_RADAR_CHECK=1` enables
in-kernel ordering assertions that flag any stage starting before its
predecessor barrier — useful when debugging scheduling regressions.

## Tuning knobs

| Flag | Default | Effect |
|------|---------|--------|
| `--gpu` | off | Link the cuFFT kernel twin instead of FFTW |
| `--workers` | 8 | Rayon worker threads |
| `--slots` | 2 | Concurrent in-flight frames (`frame_wnd`) |
| `--system-threads` | 2 | Resolution threads |
| `--receiver-threads` | 2 | Dedicated UDP receiver threads |
| `--frames` | scene | Frames to send/process |
| `--frame-period` | scene | Sender CPI interval [s] |
| `--chirp-gap-us` | scene | Inter-chirp spacing [us] (unset: `chirp_interval_s`; `0`: burst; `frame_period/n_chirps`: compressed streamed pacing) |
| `--warmup` | 10 | Leading frames excluded from timing |
| `--repeat` | 1 | Repeat each cell N times, report the per-column median (snapshots `radar_report_<tag>_rN.json`) |
| `--tiles` | 8 | Range tiles (must divide `n_samples`) |
| `--guard` / `--train` | 2 / 8 | CA-CFAR guard / training cells |
| `--pfa-scale` | 15.0 | CFAR threshold scale |
| `--sweep-workers` / `--sweep-slots` | — | Run a grid of cells |
| `--no-verify` | — | Report latency without the coverage/detection gate |
| `--no-clean` | — | Skip the Cargo clean/rebuild |

Runs use Tomii's low-latency configuration (custom scheduler, coalesced
barriers, inline continuation, slot priority, RDTSC timing).

## Output

- `results/detections_<tag>.txt` — per-frame detection dump (verifier input)
- `results/radar_report_<tag>.json` — latency summary (avg/p50/p99/p99.9,
  throughput, scheduling-overhead diagnostic)
- `results/radar_<tag>.txt` — per-node timing CSV
- `results/radar_sweep.csv` — summary row per cell (sweeps / `--csv-out`)

## CPU vs GPU

Same graph, same verifier — only the kernel `.so` changes, and latency and
throughput point in opposite directions. At the default 1024x128 CPI both
processing tails are sub-millisecond — a wash. At the 4096x512 CPI (~16x the
compute) the GPU's post-arrival latency tail is far lower and much tighter
(~0.9 ms vs ~6.9 ms p50, ~10x tighter jitter) — once the CPI is resident,
cuFFT clears it almost instantly. But *sustained frame rate* reverses: the
8-core CPU sustains ~1.85x the GPU's rate, because the GPU is capped by
per-chirp H2D + launch + stream-sync overhead (512 chirps/frame) that scaling
`--slots` barely relieves. So the kernel choice is an SLA decision — per-frame
latency/jitter (GPU) vs aggregate throughput (CPU) — measured cleanly by the
same harness. Use compressed streamed pacing (`--chirp-gap-us`
= frame_period/n_chirps) to probe the sustained-rate boundary; a burst
(`--chirp-gap-us 0`) overruns the receiver socket buffer and measures drops,
not compute.

## Layout

- `src/lib.rs` — Tomii plugin: packet parsing, network callbacks, kernel FFI
- `kernels/radar_cpu.c` — FFTW kernels; `kernels/radar_gpu.cu` — cuFFT twin
- `build_graph.py` — Python graph builder; `data/make_scene.py` — scene generator
- `sender.py` — UDP chirp streamer; `verify.py` — detection/coverage checker
- `bisect_rate.py` — sustained-frame-rate finder (compressed streamed pacing)
- `data/reference_check.py` — reference DSP the verifier's bin math matches
